# MLOps Question Bank

## Warm-up

### Q1. Walk through the ML lifecycle end to end. Where do most production ML systems actually break?
**Answer.** The lifecycle runs problem framing → data collection/preparation → experimentation/training → evaluation → deployment → monitoring → retraining, feeding back into experimentation. Most production breakage isn't in modeling — it's at the seams: training/serving skew (features computed differently offline vs online), silent data drift that no alert catches because monitoring only tracked infra metrics (latency, uptime) not model-quality metrics, and retraining pipelines that aren't actually re-run on schedule because "the model still seems fine." The failure mode to internalize: a model that trained well and passed offline evaluation degrades in production not from a code bug but from the world changing underneath a static artifact.
**Follow-ups.** Why is "the model passed all our offline tests" not sufficient evidence it'll behave well in production? → Offline tests validate against a training-time snapshot of the data distribution; production data drifts over time and offline tests can't see distribution shift, label delay, or feedback loops (the model's own predictions changing user behavior) that only manifest after deployment.

### Q2. What does MLflow actually track, and why do you need a model registry on top of experiment tracking?
**Answer.** MLflow tracking logs runs — parameters, metrics, artifacts (model files, plots), and code version — per experiment, giving you a searchable history of "what did I try and how did it do." That alone doesn't answer "which model is live in production right now" or "can I safely roll back to last week's model" — that's what the registry adds: a versioned, stage-tagged (e.g. Staging/Production/Archived) pointer to specific model artifacts, with lineage back to the run that produced them, so promotion/rollback is a metadata operation on the registry rather than a manual file-copy exercise.
**Follow-ups.** What breaks if you skip the registry and just point your serving code at "the latest run's artifact"? → You lose an explicit, auditable promotion gate — a bad run can get picked up automatically, and there's no clean way to answer "what exactly is serving traffic right now" or roll back without digging through tracking logs to find the right run ID.
**Page.** [[experiment-tracking-mlflow]]

### Q3. Why do you need a model registry distinct from experiment tracking — what does a stage transition actually enforce?
**Answer.** A stage transition (e.g. Staging → Production) is a deliberate, auditable gate — it should require passing defined promotion criteria (offline eval thresholds, a shadow-traffic comparison, sign-off) before a model artifact is allowed to serve real traffic, and it records who promoted what and when. Without this gate as an explicit registry concept, "which model is live" degenerates into tribal knowledge or whatever the last deploy script happened to point at, and rollback means finding the right artifact by hand under time pressure during an incident rather than flipping a stage pointer back.
**Follow-ups.** What's a concrete promotion criterion beyond "offline metric improved"? → A shadow deployment period where the candidate model scores requests in parallel with production (without affecting live responses) and its predictions are compared against the incumbent on real traffic distribution — catching regressions offline eval on a static test set wouldn't surface.
**Page.** [[model-registry-and-versioning]]

### Q4. What is data versioning, and why isn't "just version the code" sufficient for reproducibility?
**Answer.** Code versioning (git) captures the training logic, but a training run's actual output also depends on which exact data snapshot it saw — and datasets change (new rows appended, corrections applied, schema evolves) in ways git doesn't track. Data versioning (via a tool like Delta Lake time travel, DVC, or lakeFS) lets you pin a training run to an exact, reproducible data snapshot so "rerun this experiment" or "debug why last month's model behaved differently" doesn't hit a moving target. Without it, two people running "the same" training code on "the same" table at different times can get silently different results with no way to explain the discrepancy.
**Follow-ups.** How does Delta Lake's time travel feature give you this without a separate versioning tool? → Delta Lake keeps a transaction log of every write, so you can query a table `AS OF` a specific version or timestamp — giving you a reproducible, queryable snapshot natively within the lakehouse rather than needing to export/snapshot data into a separate versioning system.

## Core

### Q5. What specific problem do feature stores solve? Define training/serving skew precisely.
**Answer.** Training/serving skew is when a feature is computed one way in the offline training pipeline (e.g. a batch Spark job computing "average order value over 30 days" from a full historical table) and a subtly different way in the online serving path (e.g. a low-latency service approximating the same feature from a smaller cache or a different aggregation window) — the model then sees different feature semantics at inference than it trained on, degrading accuracy in a way that's hard to detect because nothing errors, the numbers are just quietly wrong. A feature store solves this by defining the feature transformation logic once and serving it through both an offline (batch, for training) and online (low-latency, for serving) path from the same definition, guaranteeing consistency instead of maintaining two independent implementations that can drift apart.
**Follow-ups.** What's the concrete cost of *not* having a feature store that teams often underestimate? → Every team/model ends up hand-rolling its own online feature computation, duplicating logic, drifting from the offline definition over time as either side gets updated independently, and skew bugs surface as unexplained accuracy degradation that takes real investigation to trace back to a feature-computation mismatch rather than a model problem.
**Page.** [[feature-stores]]

### Q6. Design a training pipeline that's repeatable and auditable. What has to be logged or parameterized rather than hardcoded?
**Answer.** Everything that could change the output needs to be an explicit, logged parameter, not a hardcoded assumption: the exact data snapshot/version used, the code commit hash, all hyperparameters, random seeds, the environment (library versions, hardware type — a GPU vs CPU run can produce different floating-point results), and the evaluation split definition. The pipeline itself should be defined declaratively (a DAG/orchestrated job, not a notebook run by hand) so re-triggering it with the same inputs is a one-command operation, and every run's full parameter set plus resulting artifact should land in the experiment tracker automatically, not via someone remembering to write it down.
**Follow-ups.** Why does "notebook run by a person" fail the auditability bar even if the person is careful? → It's not mechanically reproducible or diffable — cell execution order can differ from the visual order, intermediate state can leak between runs, and there's no forced, systematic capture of every parameter that influenced the result, so six months later nobody (including the original author) can be fully certain what actually ran.
**Page.** [[training-pipelines]]

### Q7. What does CI/CD mean for ML beyond running unit tests — what's actually different about testing data and model artifacts versus ordinary software?
**Answer.** Standard CI/CD tests code correctness against fixed expected outputs; ML CI/CD additionally needs data validation tests (schema checks, null/range checks, distribution checks on incoming data before it's allowed into training) and model validation tests (does the newly trained model beat a baseline/previous model on held-out data, does it pass fairness/bias checks, does inference latency stay within budget) — because a "passing" ML pipeline can still produce a materially worse model even though every line of code is unchanged, if the data shifted. The CD side also differs: promoting a model isn't just "deploy the new binary," it typically needs a staged rollout (shadow/canary) with automated rollback triggers on live-quality-metric regression, not just an uptime health check.
**Follow-ups.** Why is a green CI pipeline (all tests pass) not sufficient evidence a newly trained model is safe to promote? → CI tests typically check code correctness and static thresholds on a fixed eval set; they don't catch a model that's technically "passing" but has degraded on a live-traffic distribution the static eval set doesn't represent — that's what shadow/canary evaluation catches that CI alone can't.
**Page.** [[ci-cd-for-ml]]

### Q8. How do you package a model for serving? What goes wrong with "just pickle it and load it in the API"?
**Answer.** Pickling ties the artifact to the exact library versions (scikit-learn/XGBoost/PyTorch version) and often the exact Python version used to create it — load it in a slightly different environment and you get silent numerical differences or an outright deserialization error, sometimes only surfacing much later on an obscure code path. Proper packaging captures the full inference environment as a reproducible unit (a container image, or an MLflow model format with its declared conda/pip environment) bundling the model artifact, the exact dependency versions, and the preprocessing logic needed to go from raw request to model input — so "it works on my machine" isn't a risk at serving time.
**Follow-ups.** Why must preprocessing logic travel with the model artifact rather than living separately in the serving service's code? → If preprocessing (encoding, scaling, tokenization) is reimplemented separately in the serving code instead of packaged with the model, any drift between the training-time and serving-time preprocessing is exactly a training/serving skew bug — bundling it as one artifact removes that entire class of error.
**Page.** [[model-packaging-and-containers]]

### Q9. Batch versus real-time inference — how do you decide, and what changes architecturally?
**Answer.** The decision hinges on whether a prediction is needed synchronously in response to a live user action (real-time — a recommendation shown on page load, a fraud check blocking a transaction) or can be precomputed on a schedule and looked up later (batch — nightly churn scores, weekly demand forecasts). Real-time serving needs a low-latency online service (a model server behind an API, often with the model warm in memory), tight latency SLAs, and typically simpler/smaller models or optimizations (quantization, smaller architectures) to hit latency budgets; batch inference can use arbitrarily heavier models since it runs on a schedule with generous time budgets, and results are just written to a table for downstream lookup, trading freshness (predictions can be hours/a day stale) for much lower operational complexity and cost per prediction.
**Follow-ups.** What's a hybrid pattern that gets the benefit of both? → Precompute batch scores for the common/predictable case (e.g. nightly recommendations for all users) and fall back to real-time inference only for cold-start or clearly time-sensitive cases (a brand-new user or item with no batch score yet) — most of the traffic gets cheap batch predictions, only the genuinely latency-sensitive slice pays for real-time serving.
**Page.** [[batch-vs-realtime-inference]]

### Q10. What's the single most-asked MLOps interview topic — model monitoring — and what do you actually monitor beyond accuracy?
**Answer.** You monitor at three layers because accuracy alone (which usually needs ground-truth labels that arrive late or never) can't be your only signal: (1) operational/infra metrics — latency, throughput, error rate, resource usage, same as any service; (2) input/data metrics — feature distribution drift versus the training distribution, missing-value rates, schema violations on incoming requests, which can be computed immediately without waiting for labels; (3) output/prediction metrics — prediction distribution shift (is the model suddenly predicting a very different class mix), confidence-score distribution shift, and business-outcome proxies that correlate with quality (click-through, conversion) as a faster-arriving signal than ground-truth labels. Combining these gives you an early-warning system that doesn't depend entirely on delayed labels to notice something's wrong.
**Follow-ups.** Why is prediction-distribution monitoring valuable even when you have no ground truth yet? → A sudden shift in the model's output distribution (e.g. it starts predicting "fraud" on 40% of transactions instead of the usual 2%) is a strong, immediately-available signal that something changed — either the input distribution shifted or the model/pipeline broke — without needing to wait for the eventual fraud-confirmation labels to arrive.
**Page.** [[model-monitoring]]

### Q11. Explain data drift versus concept drift with an example each, and how you'd detect each statistically.
**Answer.** Data drift (a.k.a. covariate shift) is when the input feature distribution changes but the true relationship between features and target stays the same — e.g. a fraud model sees a shift toward more mobile-app transactions relative to web, without the actual fraud patterns changing; detect it with distribution-comparison tests on feature values over time (population stability index, KL divergence, or a two-sample KS test between a reference window and a current window). Concept drift is when the relationship between features and target itself changes — e.g. fraudsters adopt a genuinely new tactic, so the same feature values that used to indicate "legitimate" now indicate "fraud"; this is harder to detect directly since it needs labels (monitoring the model's accuracy/error rate over time, since the input distribution can look stable while accuracy silently degrades) rather than just input-distribution monitoring.
**Follow-ups.** Why can data drift monitoring alone completely miss a concept drift problem? → Input feature distributions can look perfectly stable (no PSI/KS alarm) while the underlying feature-target relationship has shifted — you'd only catch that by monitoring actual prediction accuracy against (possibly delayed) ground truth, which is exactly why relying only on input-drift dashboards gives false confidence.
**Page.** [[data-drift-and-concept-drift]]

### Q12. Monitoring flags drift on a live model. What's your retraining strategy — scheduled versus triggered, and how do you validate the new model before it replaces the old one?
**Answer.** Scheduled retraining (e.g. weekly, regardless of detected drift) is simple and predictable but wastes compute when nothing's changed and can be too slow to react to a sudden real shift; triggered retraining (kick off a retrain when a monitoring metric crosses a threshold) reacts faster but needs the trigger logic itself to be well-tuned (too sensitive and you retrain on noise, too loose and you miss real drift) — most mature setups run both, a baseline schedule plus an alert-triggered early retrain. Before the new model replaces the old one, it needs to clear the same promotion gate as any model change: beat the incumbent on a held-out and, ideally, on live shadow traffic, not just pass an internal offline metric — you're not just checking "is this a good model," you're checking "is this better than what's currently live, on data representative of what's live right now."
**Follow-ups.** What's the risk of retraining directly on recent production data that includes the drift you're reacting to? → If the drift includes a temporary anomaly (a one-off event, a logging bug that briefly corrupted a feature) rather than a genuine persistent shift, retraining on it can bake in a distortion rather than correcting for a real, lasting change — worth distinguishing transient anomalies from persistent drift before deciding retraining is even the right response versus just fixing an upstream data bug.
**Page.** [[model-retraining-strategies]]

### Q13. Walk through shadow deployment versus canary deployment — what's the actual risk profile of each?
**Answer.** Shadow deployment runs the new model in parallel with the live model on real production traffic, computing its predictions but never returning them to users (only the incumbent's predictions are served) — zero user-facing risk, purely for comparing behavior on real traffic before any exposure, at the cost of extra compute (running two models per request) and not testing anything about actual user reaction to the new model's outputs. Canary deployment routes a small real percentage of live traffic (e.g. 5%) to the new model's actual served predictions, so it does carry real risk (a bad model affects real users) but is bounded to a small slice and lets you observe true end-to-end impact (including downstream effects a shadow test can't see, like how users react to different recommendations) before a full rollout, with an automated rollback if canary metrics regress.
**Follow-ups.** Why would you use both in sequence rather than picking just one? → Shadow catches gross behavioral problems at zero user risk before anything is exposed; canary then validates the parts shadow structurally can't test (actual user response, downstream system effects of served predictions) with bounded, monitored exposure — sequencing them catches different failure classes at increasing but controlled risk.

## Hard

### Q14. A stakeholder asks you to cut ML infrastructure cost by 30% without hurting SLAs. What levers do you actually pull, and in what order?
**Answer.** Start by measuring where cost actually goes (compute for training vs serving vs storage vs data pipeline runs) rather than guessing — serving cost usually dominates for high-traffic models since it's continuous, while training is a periodic spike. High-leverage, low-risk levers first: right-size serving instances/autoscaling policies against actual traffic patterns (many teams over-provision for a peak that rarely occurs), enable batch inference wherever real-time isn't actually required (moves cost off the always-on expensive path), and cache repeated/identical inference requests. Higher-impact but riskier levers next: model compression (quantization, distillation, pruning) to cut serving compute per request, which needs re-validation of accuracy/latency tradeoffs before shipping, and consolidating redundant pipeline runs (are multiple teams recomputing the same features independently). The order matters because the first tier is close to risk-free while the second tier can regress quality if not carefully validated — you don't want a cost-cutting exercise to quietly become an SLA-breaking one.
**Follow-ups.** Why is "just use a smaller/cheaper model" often the wrong first lever despite being the most obvious one? → It directly trades off against the quality/SLA constraint you were told not to hurt, and re-validating a smaller model's accuracy takes real time — whereas infra right-sizing and batch/caching wins are usually free accuracy-wise and available immediately, so they should be exhausted before touching the model itself.
**Page.** [[cost-optimization-for-ml]]

### Q15. What does testing strategy look like for ML systems beyond standard software unit tests?
**Answer.** Standard unit tests check code logic against fixed expected outputs, which is necessary but doesn't catch ML-specific failure classes: data tests (schema/type/range/null checks on incoming data, run as a pipeline gate before training or serving ever sees bad data), model quality tests (does a newly trained model beat a fixed baseline/minimum bar on held-out data — a regression test for model quality, not just code), behavioral/invariance tests (does the model's prediction stay appropriately stable under a semantically-irrelevant perturbation — e.g. a sentiment model shouldn't flip its prediction just because a name was changed from "John" to "Maria," which also doubles as a basic fairness check), and slice-based tests (does accuracy hold up on specific important subpopulations, not just the aggregate metric, which can hide a subgroup where the model is badly wrong).
**Follow-ups.** Why is aggregate accuracy alone an insufficient test even when it looks good? → A model can hit a strong overall accuracy number while performing badly on a specific, business-critical slice (a minority class, a particular customer segment) that's underrepresented in the aggregate — slice-based testing is what actually surfaces that, and it's a common way "the tests passed" and "the model was still bad for a lot of real users" coexist.
**Page.** [[ml-testing-strategy]]

### Q16. Two runs of "the same" training job produce different metrics despite identical code and data. Walk through every source of nondeterminism you'd check.
**Answer.** Check, roughly in order of likelihood: (1) random seeds not fixed across every source of randomness (numpy, framework-level RNG, data shuffling order, and — often missed — the seed for train/validation splitting itself); (2) GPU non-determinism — certain cuDNN operations are non-deterministic by default for performance reasons unless you explicitly set deterministic-mode flags, and results can differ across GPU models/driver versions even with identical seeds; (3) parallelism/ordering effects — multi-threaded data loading or distributed training can process examples in a different order run to run, which matters for algorithms sensitive to batch composition/order; (4) library/environment version drift — a patch version bump in a training library can silently change default hyperparameters or numerical implementation details; (5) "identical data" that actually isn't — a data source that's technically mutable (a table that received a late-arriving update) between the two runs despite both claiming to use "the same" table, which is exactly why data versioning/snapshotting matters. Reproducibility requires pinning all of these, not just the obvious random seed.
**Follow-ups.** Why might you deliberately choose not to force full bitwise determinism even when it's technically achievable? → Deterministic GPU operations are often meaningfully slower than their non-deterministic optimized counterparts, so forcing full determinism trades training speed for exact reproducibility — a reasonable call for debugging a specific discrepancy, but often not worth paying for every routine training run.
**Page.** [[reproducibility]]

### Q17. How does Unity Catalog change access control and lineage for ML artifacts compared to a plain data lake with no unified governance layer?
**Answer.** Without a unified catalog, access control is typically enforced inconsistently per-tool (storage-level ACLs for raw files, separate permissions in the notebook environment, yet another scheme in the serving system), and lineage (which upstream table/version fed which model, and which downstream model consumed a given feature) has to be manually reconstructed from logs or tribal knowledge when you need to answer "what's affected if we change this table" or trace a data-quality incident back to its source. Unity Catalog centralizes access control across data, features, and models under one permission model (grants that apply consistently whether you're querying via SQL, a notebook, or a model-serving endpoint) and automatically tracks lineage end-to-end — table → feature → model → endpoint — so you can answer both "who can access this" and "what depends on this" as a governance-layer query rather than an investigation.
**Follow-ups.** Why does this matter especially for regulated/PII-sensitive data in an Indian enterprise/GCC context? → Compliance requirements (audit trails, data-access justification, the ability to prove exactly who accessed sensitive data and trace any model back to the data it was trained on) become a query against the catalog's built-in lineage and access logs instead of a manual reconstruction exercise during an audit — critical when a regulator or client asks "prove this model never saw data it wasn't authorized to see."

### Q18. How do MLOps practices change for LLM-based systems (LLMOps) — what's genuinely different from classic model monitoring and deployment?
**Answer.** Classic MLOps monitors a model with a fixed, well-defined input/output schema and stable statistical behavior; LLM systems break several of those assumptions. Evaluation is harder because outputs are open-ended text rather than a class label or number, so you need LLM-judge-based or human-rated evaluation rather than simple accuracy, and "ground truth" is often fuzzy or absent. Cost and latency monitoring matter differently — you're tracking per-token cost and prompt/completion length distributions, not just request count, and a prompt template change (not a model retrain) can shift behavior just as much as a model swap, meaning prompt versions need the same registry/rollback discipline as model versions. Deployment often means swapping or updating a hosted third-party API's model version (outside your control, e.g. a provider deprecating a model) rather than deploying your own retrained artifact, which changes the risk profile — you monitor for a *provider-side* silent model update degrading your system, not just your own retraining cycle.
**Follow-ups.** Why does "the same prompt" not guarantee "the same behavior" over time the way a deployed model artifact would? → If you're calling a hosted API, the provider can update the underlying model version behind the same endpoint/model name without you retraining anything — your system's behavior can drift purely from a change entirely outside your deployment pipeline, which is why LLMOps needs its own version-pinning and regression-testing discipline against provider-side model updates, not just your own prompt/config changes.
