## Warm-up

### Q1. Explain how byte-pair encoding (BPE) builds a vocabulary, and why subword tokenization beats word-level or character-level tokenization.
**Answer.** BPE starts from individual characters/bytes, then iteratively finds the *most frequent adjacent pair* of tokens in the corpus and merges them into a new single token, repeating until a target vocabulary size is reached — common substrings/words end up as single tokens while rare ones stay split into smaller pieces. Word-level tokenization needs a huge vocabulary and still hits out-of-vocabulary words at inference; character-level avoids OOV entirely but produces very long sequences (expensive for quadratic attention) and forces the model to relearn morphology from scratch. Subword tokenization gets a bounded vocabulary, handles unseen words by falling back to smaller known pieces, and keeps sequences reasonable.
**Follow-ups.** Why does BPE handle multilingual/code-mixed text worse than a language-specific tokenizer, and what does SentencePiece change? → A vocabulary trained mostly on one language allocates fewer/larger merge units to under-represented languages, inflating sequence length for them; SentencePiece treats input as a raw, language-agnostic byte/Unicode stream with no whitespace-word assumption, handling languages without spaces (Chinese, Japanese) more naturally.

### Q2. Derive the skip-gram objective in word2vec, and explain what contextual (BERT-style) embeddings add that static embeddings fundamentally cannot.
**Answer.** Skip-gram maximizes $\sum_t\sum_{-c\le j\le c,j\ne0}\log P(w_{t+j}|w_t)$ where $P(w_O|w_I)=\frac{\exp(v_{w_O}'^Tv_{w_I})}{\sum_w\exp(v_w'^Tv_{w_I})}$ (approximated via negative sampling instead of full softmax). This yields exactly one fixed vector per word type regardless of context, so "bank" gets the same embedding whether riverbank or financial institution. Contextual embeddings compute a representation as a function of the *entire input sequence* at inference time (via self-attention over all tokens), so the same word gets a different vector depending on surrounding context — resolving polysemy static embeddings structurally cannot.
**Follow-ups.** Why can static embeddings still be preferable in some production settings? → A single lookup table with no forward pass needed makes them vastly cheaper/faster for latency-sensitive similarity tasks where polysemy disambiguation isn't the bottleneck.
**Page.** [[word-embeddings-word2vec-glove]]

### Q3. Contrast causal and masked language modeling objectives, and explain why decoder-only models became the basis for general-purpose chat LLMs.
**Answer.** Causal LM predicts each token given only tokens *before* it ($P(x_t|x_{<t})$) via a triangular attention mask — this exactly matches the generation-time task, so training and deployment objectives are identical. Masked LM (BERT) corrupts ~15% of tokens and predicts them using *bidirectional* context — better for representations feeding classification/retrieval, but there's no natural way to generate left-to-right from a bidirectional model. Because the end goal (open-ended generation, chat) is inherently sequential, causal LM's training-inference match made decoder-only architectures the natural fit, while encoders kept their edge for fixed-size whole-input representations.
**Follow-ups.** Why can encoder-only models see bidirectional context during training without "cheating," while a causal model would if allowed to? → BERT never generates sequentially at inference — it only needs a final representation computed once with the full unmasked input, matching its deployed use case; a causal model's deployed use case is sequential generation, so bidirectional training context would let it "see the answer" it must learn to predict from scratch.
**Page.** [[language-modeling-objectives]]

### Q4. Why is a BERT-style encoder still the default for a retrieval/classification embedding model even in an LLM-heavy stack?
**Answer.** BERT's bidirectional attention over the full input in one pass produces a representation optimized to summarize the entire sequence, and pooling (CLS token, mean pooling) gives exactly the fixed-size vector a retrieval encoder needs — computed cheaply (one pass, no autoregressive decoding) at far smaller parameter counts, making it cheap to embed millions of documents. A decoder-only LLM's causal masking means later tokens don't see earlier tokens' fully-updated context the way every token in a bidirectional encoder does, and using a generative LLM purely for embeddings wastes most of its capability and compute budget.
**Follow-ups.** What's the tradeoff of a bi-encoder versus a cross-encoder for retrieval? → Bi-encoders embed query and documents independently, enabling fast ANN search over a precomputed index at massive scale; cross-encoders jointly attend over the concatenated pair (more accurate ranking) but need a full forward pass per candidate, too slow over a whole corpus — hence bi-encoder retrieval followed by cross-encoder reranking.
**Page.** [[bert-and-encoder-models]]

### Q5. Walk through how a GPT-style decoder generates text token by token, and explain why this is fundamentally sequential even though training was parallelized.
**Answer.** At each step, the model takes all tokens so far, runs a full causal self-attention forward pass, and produces a distribution over the next token from the final position's logits; a token is sampled, appended, and the process repeats — each new token's representations depend on the *actual* previous token being available, so step $t+1$ can't start before step $t$'s output is chosen. During training, the entire target sequence is known in advance (teacher forcing), so all positions' losses are computed in one parallel pass using true previous tokens — that parallelism exploits information (the whole ground-truth sequence) that doesn't exist yet during generation.
**Follow-ups.** How does KV-caching reduce the *cost* of each sequential step without removing the sequential dependency? → It caches previous tokens' key/value projections so each new step computes attention for only the one new query against cached keys/values, cutting per-step compute from $O(n^2)$ to $O(n)$ — but generation is still one token at a time because the next token's identity is required before it can be embedded and cached.
**Page.** [[gpt-and-decoder-models]]

## Core

### Q6. State the Chinchilla scaling-law finding and explain why many earlier large models were compute-inefficient for their size.
**Answer.** For a fixed training compute budget, loss is minimized not by maximizing parameter count alone but by scaling model size and training-token count together, roughly ~20 tokens per parameter — earlier models trained on far fewer tokens relative to parameter count meant a smaller model on proportionally more data would reach the same loss for the same compute, or the same loss more cheaply. Intuition: an oversized model trained on too little data hasn't received enough gradient signal to use its capacity — compute on extra parameters is wasted relative to spending it on more tokens for a right-sized model.
**Follow-ups.** Why would a company deliberately train a "Chinchilla-suboptimal" model anyway? → Inference cost scales with parameter count and is paid repeatedly over the model's deployed lifetime, while training cost is paid once — so for high-volume serving it can be cheaper overall to overtrain a smaller model past the compute-optimal token count in exchange for cheaper long-term serving.
**Page.** [[llm-scaling-laws]]

### Q7. Explain what a base pretrained LLM cannot reliably do that SFT fixes, and why more pretraining data alone doesn't solve it.
**Answer.** A base model predicts the statistically likely next token given internet-scale text — given a question, its most probable continuation might be a related question or a list of similar questions, because "answer helpfully and directly" was never the objective. SFT trains directly on the *behavior* wanted (respond to an instruction with a helpful, on-topic answer), reshaping the conditional distribution without needing to relearn world knowledge, since that's already encoded from pretraining. More raw pretraining text doesn't fix this because the objective mismatch (predict plausible text vs. behave as an assistant) is present regardless of scale.
**Follow-ups.** Why is SFT data quality typically prioritized over quantity, unlike pretraining? → SFT datasets are orders of magnitude smaller and meant to demonstrate a narrow behavior pattern rather than teach facts — a small set of clean, consistent examples shapes behavior more reliably than a larger noisy set that can actively teach conflicting response styles.
**Page.** [[instruction-tuning-and-sft]]

### Q8. Describe the RLHF pipeline (reward model + PPO) end to end, and name the "reward hacking" failure mode it's prone to.
**Answer.** Three stages: (1) SFT for a reasonable starting policy, (2) train a reward model on human preference comparisons via a Bradley-Terry-style loss so it scores preferred outputs higher, (3) use PPO to fine-tune the SFT model to maximize the learned reward, with a KL penalty against the original SFT policy preventing degenerate drift. Reward hacking happens because the reward model is only a learned proxy trained on finite, imperfect comparisons — PPO exploits any systematic blind spot (e.g. rewarding verbosity because the reward model was biased toward length) even though it doesn't reflect true human preference, since optimization pressure targets the proxy, not the real objective.
**Follow-ups.** Why does the KL penalty only partially mitigate reward hacking rather than eliminate it? → It bounds how far the policy can drift from the reference model but doesn't correct the reward model's blind spots — the policy can still drift within that bounded region toward whatever local exploit exists, just more slowly.
**Page.** [[rlhf]]

### Q9. Derive how DPO reformulates the RLHF objective to skip the reward model and PPO loop, and state the assumption that makes this valid.
**Answer.** RLHF's KL-regularized objective has a known closed-form optimal policy: $\pi^*(y|x)\propto\pi_{ref}(y|x)\exp(r(x,y)/\beta)$. Inverting it expresses reward implicitly via the policy: $r(x,y)=\beta\log\frac{\pi^*(y|x)}{\pi_{ref}(y|x)}+\text{const}$. Substituting into the Bradley-Terry preference formula turns the reward-modeling loss directly into a loss over the *policy's own* log-probabilities of preferred vs. dispreferred responses — so DPO trains the policy directly on preference pairs with a simple classification-style loss, no separate reward model or RL rollout. This is valid because of the assumed one-to-one correspondence between reward functions and their KL-regularized-optimal policies under the same reference model.
**Follow-ups.** What practical instability does DPO avoid that made PPO-based RLHF fragile to tune? → PPO requires online sampling from the current policy, scoring it with the reward model, and tuning the KL coefficient/clipping to avoid collapse or reward hacking — an unstable multi-model loop; DPO is a single supervised-style loss on a fixed offline dataset, with far fewer moving pieces to destabilize.
**Page.** [[dpo-and-preference-optimization]]

### Q10. Derive the parameter savings from LoRA, and explain why a low-rank update doesn't cripple the model's ability to adapt.
**Answer.** Instead of fine-tuning the full $W\in\mathbb{R}^{d\times k}$ ($dk$ trainable parameters), LoRA freezes $W$ and learns $\Delta W=BA$ where $B\in\mathbb{R}^{d\times r}$, $A\in\mathbb{R}^{r\times k}$ for small rank $r\ll\min(d,k)$ — trainable parameters drop from $dk$ to $r(d+k)$, often >100x for typical $r$ (4-64). This works because the effective weight change needed to specialize a pretrained model to a new task empirically has low intrinsic rank — the pretrained weights already encode most necessary structure, so adaptation is more a small structured correction within a low-dimensional subspace than a wholesale rewrite.
**Follow-ups.** Why can LoRA adapters be merged into base weights at zero added inference latency, unlike some other PEFT methods? → $\Delta W=BA$ has the same shape as $W$, so $W'=W+BA$ can be computed once offline and served directly — no separate adapter module or extra forward-pass branch remains at inference, unlike methods with an always-on extra computation path.
**Page.** [[parameter-efficient-finetuning-lora]]

### Q11. Explain the arithmetic of int8 quantization for LLM weights, and why naive uniform quantization sometimes causes outsized accuracy loss.
**Answer.** Basic quantization maps values to 256 int8 levels via a scale factor: $q=\text{round}(w/s)$, $s=\max(|w|)/127$ — memory drops 2-4x versus fp16, and int8 matmuls run faster on dedicated low-precision hardware kernels. The problem: LLM weight/activation distributions often have a small number of extreme outliers, and a single global scale calibrated to cover them wastes most of int8's 256 levels on a huge range, leaving poor precision for the bulk of normal values near zero. Per-channel quantization (separate scale per output channel) and outlier-aware schemes (keeping extreme values in higher precision) fix this by not letting a handful of outliers force a coarse scale onto everything else.
**Follow-ups.** Why is quantizing activations harder than quantizing weights? → Weights are static and can be calibrated once offline; activations vary per input at runtime, so their dynamic range must be estimated on the fly or via a calibration set and can shift across inputs in ways a fixed scale factor doesn't handle well, especially for outlier-heavy dimensions.
**Page.** [[quantization]]

### Q12. Contrast greedy decoding, beam search, and nucleus (top-p) sampling, and explain why greedy/beam search can produce repetitive text despite maximizing sequence likelihood.
**Answer.** Greedy picks the single highest-probability token each step; beam search keeps the top-$k$ partial sequences by cumulative log-probability, extending and pruning — both approximate the most-likely overall sequence. But the most-likely sequence under an LM is empirically not the most human-like: high-likelihood text tends toward generic, repetitive phrasing, since beam search's cumulative-probability objective favors reusing already-likely continuations, producing loops. Nucleus sampling instead samples from the smallest token set whose cumulative probability exceeds $p$, renormalizing over just that nucleus — preserving genuine diversity while cutting the unreliable low-probability tail.
**Follow-ups.** Why is temperature applied before top-p/top-k rather than after? → Temperature rescales logits ($z/T$) before softmax, reshaping the entire distribution's sharpness; top-p then selects the nucleus from that reshaped distribution, so the two controls compose — temperature sets confidence, top-p bounds which tail is eligible.
**Page.** [[decoding-strategies]]

### Q13. Why does effective prompt engineering require the same rigor as feature engineering rather than finding the right "trick"?
**Answer.** A prompt shapes the input to a black-box function (the model), so the only reliable way to know a prompting change helped is to define the task's success metric, build a representative eval set with expected outputs/rubrics, and A/B prompt variants against it — the same discipline as evaluating a feature or model change, with the model side held fixed. Techniques like few-shot exemplars or chain-of-thought are hypotheses about what conditioning helps retrieval/reasoning, and each needs validating on the actual downstream distribution — a trick that works on one example set can regress on another due to distributional differences, the same way an overfit feature regresses out-of-sample.
**Follow-ups.** Why do few-shot examples sometimes hurt performance versus zero-shot? → Poorly chosen exemplars can bias the model toward their surface pattern (format, length, reasoning style) rather than the underlying task logic, narrowing the response space in a way that mismatches the true input distribution — which is why exemplar selection/ordering are treated as tunable hyperparameters, evaluated empirically.
**Page.** [[prompt-engineering]]

## Hard

### Q14. Derive the memory cost of the KV cache during generation, and explain why this — not raw compute — becomes the binding constraint on serving throughput for long contexts.
**Answer.** For $L$ layers, $h$ heads of dimension $d_h$, the KV cache stores one key and value vector per token per layer per head: memory $=2\times L\times h\times d_h\times n\times\text{(bytes/value)}$ for sequence length $n$ — growing linearly with both sequence length and batch size (each concurrent request needs its own cache), reaching many GB at fp16 for a modern multi-billion-parameter model and long sequences. Because the cache must stay resident in GPU memory alongside model weights for every token generated across every concurrent request, it directly competes with weights for the same fixed memory budget — past a certain context length/batch size, memory runs out before compute does, so achievable batch size (and throughput) is capped by cache memory, not FLOPs.
**Follow-ups.** Name two techniques that specifically target reducing KV cache size rather than raw FLOPs. → Multi-query/grouped-query attention (sharing key/value projections across query heads, cutting cache size roughly by the number of heads sharing them) and quantizing the KV cache itself to int8 — both directly shrink per-token cache footprint.
**Page.** [[kv-cache-and-inference-optimization]]

### Q15. Explain what FlashAttention changes about computing attention — is it an approximation — and why it speeds things up despite doing the same number of FLOPs.
**Answer.** FlashAttention computes exactly the same result as standard attention — not an approximation — but changes the memory-access pattern: instead of materializing the full $n\times n$ score matrix in GPU HBM and reading/writing it repeatedly across softmax and weighted-sum steps, it tiles the computation into blocks that fit in fast on-chip SRAM, computing partial softmax statistics incrementally (the online/streaming softmax trick) and never writing the full matrix back to HBM. Standard attention is memory-bandwidth-bound, not compute-bound, on modern GPUs — eliminating the large HBM traffic (while doing identical arithmetic) yields a substantial wall-clock speedup and reduces peak memory from $O(n^2)$ to $O(n)$.
**Follow-ups.** Why couldn't this trick be applied trivially before FlashAttention identified it? → Softmax's normalization requires the sum over the entire row before finalizing any output, so naive tiling seems to need the full row in memory first; the online-softmax reformulation maintains a running max and sum incrementally across tiles and algebraically corrects earlier partial results as new tiles arrive, avoiding ever materializing the full row.
**Page.** [[flash-attention-and-efficient-attention]]

### Q16. Explain the mixture-of-experts architecture and the load-balancing problem a naive top-k router creates, and how an auxiliary loss addresses it.
**Answer.** An MoE layer replaces a single dense FFN with many parallel expert FFNs plus a lightweight router that, per token, scores each expert and routes to only the top-$k$ (often 1-2) — decoupling total parameter count from compute cost per token, letting total capacity scale far beyond dense compute budgets. Left unconstrained, the router tends to collapse onto a small subset of experts early in training (experts getting more tokens early get more gradient signal, attracting even more routing weight), leaving other experts undertrained while favored ones are overloaded. An auxiliary load-balancing loss penalizes this imbalance directly — encouraging the routing distribution across experts to stay close to uniform — added to the main task loss.
**Follow-ups.** Why does MoE reduce serving compute per token but not necessarily serving memory? → All experts' weights must reside in memory since which experts a token routes to isn't known until the router runs, so total memory scales with total parameter count across all experts even though only a fraction compute for any single token — MoE trades memory/parameter-count for compute efficiency, not shrinking overall resource needs.
**Page.** [[mixture-of-experts]]

### Q17. Explain how RoPE injects position information differently from sinusoidal absolute positional encoding, and why this helps generalize to longer contexts than seen in training.
**Answer.** Sinusoidal absolute PE adds a fixed position-dependent vector to each token embedding before attention — position is baked in additively, and the model must indirectly learn relative-position relationships from these absolute encodings. RoPE instead *rotates* each query/key vector by an angle proportional to its absolute position, applied multiplicatively right before the attention dot product; because a dot product of two rotated vectors depends only on the *difference* between their rotation angles, the attention score $q_m^Tk_n$ ends up depending on relative position $(m-n)$ directly and analytically, not on absolute positions separately. This generalizes better beyond training length since attention is mathematically a function of relative offset, a quantity that doesn't inherently change just because absolute sequence length grows.
**Follow-ups.** Why does RoPE still degrade at context lengths far beyond training despite this property? → The rotation frequency bands were calibrated for the relative-position ranges seen in training, so extremely long offsets rotate through many full cycles and start aliasing — which is exactly what NTK-aware scaling or position interpolation fix by rescaling rotation frequencies for longer contexts.
**Page.** [[context-window-and-positional-encoding]]

### Q18. Explain why RAG reduces but does not eliminate hallucination, and name the failure modes that persist even with a working retrieval pipeline.
**Answer.** RAG grounds generation in retrieved documents rather than relying purely on parametric memory, but the LLM remains generative and free to ignore, misread, or over-extrapolate beyond retrieved content — it can still synthesize a plausible but unsupported claim by blending retrieved content with prior knowledge, especially when context is incomplete or ambiguous. Persisting failure modes: retrieval failure (the relevant document isn't in the top-$k$ chunks, leaving the model to fall back on its parametric guess), context conflict (retrieved documents disagree with each other or the model's trained knowledge, with no principled arbitration), and faithfulness failure (the model attends to retrieved context but still generates an unsupported claim — a distinct problem from retrieval quality).
**Follow-ups.** How would you test whether a RAG system's hallucination is a retrieval problem or a faithfulness problem? → Feed the model the gold supporting document directly, bypassing the retriever, and check if the answer becomes faithful — if yes, the fault was retrieval; if it still fabricates or contradicts the correct context, the fault is generation-time faithfulness, requiring a different fix (citation-constrained decoding, a faithfulness classifier as a guard).
