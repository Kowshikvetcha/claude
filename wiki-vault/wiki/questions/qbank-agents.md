## Warm-up

### Q1. What actually makes a system "agentic" versus a fancy chained prompt (a fixed pipeline of LLM calls)?
**Answer.** A chained pipeline has a hardcoded sequence of steps decided at design time — step 2 always follows step 1 regardless of what step 1 returned. An agent has a control loop where the *model itself* decides the next action (which tool, which sub-goal, whether to stop) conditioned on the outcome of the previous action, so the execution graph is only known at runtime. The dividing line in practice: can the system take a variable number of steps, in a variable order, in response to intermediate results? If yes, it's agentic.
**Follow-ups.** Is a single LLM call with one tool and no loop "agentic"? → No — no dynamic control flow, it's a function call with extra steps; agentic requires at least an observe-decide loop that can branch.

### Q2. Walk through the mechanics of tool calling: what does the model actually output, and who executes the tool?
**Answer.** The model is given a set of tool schemas (name, description, JSON-schema-typed parameters) in its context/system prompt. Instead of emitting free text, it emits a structured request — typically JSON matching one schema — naming the tool and arguments. The *host application*, not the model, parses that JSON, executes the real function (an API call, a DB query, code execution), and feeds the result back into the conversation as a new message, after which the model continues generating. The model never runs anything itself; it only ever produces a request for the harness to run.
**Follow-ups.** What happens if the model emits arguments that don't validate against the schema? → The harness should reject and return a structured error back into context (not silently retry with defaults) so the model can self-correct on the next turn — most frameworks do one or two bounded repair attempts before failing the step.
**Page.** [[tool-calling-and-function-schemas]]

### Q3. Explain the ReAct loop and why interleaving reasoning traces with actions helps over just calling tools directly.
**Answer.** ReAct alternates Thought → Action → Observation: the model writes a short reasoning trace about what to do next, emits one tool call, gets the result appended to context, and repeats. The reasoning trace matters because it forces the model to commit to an explicit plan token-by-token before acting, which measurably reduces impulsive/wrong tool calls compared to action-only prompting, and it also gives you a human-readable audit trail of *why* a given tool was called — critical for debugging a bad trajectory after the fact.
**Follow-ups.** What's the failure mode when the loop has no termination check? → It runs to the max-steps budget doing token-burning busywork ("reflection loops") — you need an explicit stop condition (goal-achieved check or a hard step cap) independent of the model deciding to stop on its own.
**Page.** [[react-and-reasoning-loops]]

### Q4. What's the difference between an agent's short-term and long-term memory, and why can't you just keep stuffing everything into the context window?
**Answer.** Short-term memory is the current conversation/trajectory living in the context window — it's free (no extra retrieval step) but bounded and lost when the session ends. Long-term memory is anything persisted outside the context window (a vector store of past interactions, a structured user-profile store, episodic summaries) that gets selectively retrieved back in. You can't just keep appending everything because context is finite and costs scale with it, and past a certain length models degrade at using information buried in the middle ("lost in the middle"), so an ever-growing raw transcript actively hurts quality, not just cost.
**Follow-ups.** How do you decide what goes from short-term into long-term memory rather than being discarded? → Typically a summarization/extraction step at session boundaries pulls out durable facts (user preferences, decisions made, entities referenced) into a structured store, while the verbatim turn-by-turn transcript is dropped.

## Core

### Q5. How do you decompose a complex multi-step goal into subtasks, and what specifically goes wrong when the decomposition is bad?
**Answer.** The common pattern is plan-then-execute: an initial planning call produces a task list/DAG, then each subtask is executed (possibly by re-planning after each step given new information — "replanning" vs a static upfront plan). What goes wrong: (1) *error propagation* — a wrong assumption in step 1 silently corrupts every downstream step because nothing re-validates earlier assumptions; (2) *over-decomposition* — splitting a task so finely that coordination/context-passing overhead between subtasks exceeds the benefit; (3) *brittle ordering* — a static plan that can't adapt when step 3's real-world result invalidates the assumption step 5 was planned on.
**Follow-ups.** Static upfront planning vs interleaved planning — when do you prefer each? → Static plans are cheaper and more predictable for well-understood, low-uncertainty tasks; interleaved (re-plan after each observation) costs more tokens/latency but is necessary when the environment is only partially known upfront (e.g. web research where each search result changes what's worth searching next).
**Page.** [[planning-and-task-decomposition]]

### Q6. What problem does Model Context Protocol (MCP) actually solve — why not just have every agent framework write custom tool integrations?
**Answer.** Before MCP, every agent framework (LangChain, LlamaIndex, a custom harness) needed its own bespoke adapter for every external system (Slack, Postgres, GitHub), giving an M×N integration problem — M frameworks times N tools. MCP standardizes the interface between a model-facing "client" (the agent host) and a "server" (a tool/data provider) so one MCP server implementation works with any MCP-compliant client, collapsing M×N into M+N. It's transport- and schema-standardized (JSON-RPC over stdio or HTTP/SSE), covering tools, resources (readable context/data) and prompts as first-class primitives, not just function calls.
**Follow-ups.** What's the actual security surface MCP introduces that a hardcoded integration doesn't? → A malicious or compromised MCP server can return tool descriptions or results crafted to manipulate the agent (prompt injection via tool output), and because MCP servers are often installed from third parties, you're trusting arbitrary code with whatever the client exposes — so scoping permissions per-server and treating tool outputs as untrusted data matters more than with a single audited in-house integration.
**Page.** [[model-context-protocol]]

### Q7. Compare a hand-rolled ReAct loop, a graph-based framework like LangGraph, and a multi-agent framework like AutoGen/CrewAI — what's the actual tradeoff?
**Answer.** A hand-rolled loop gives full control and zero abstraction overhead but you own every edge case (retries, state persistence, streaming) yourself — fine for a narrow, well-understood task. LangGraph models the agent as an explicit state machine/graph with typed nodes and edges, which buys you visualized control flow, checkpointing, and human-in-the-loop interrupts at defined nodes, at the cost of upfront modeling effort. AutoGen/CrewAI abstract at the multi-agent-conversation level (define roles, let agents message each other), which is fast to prototype a multi-persona workflow but hides the actual control flow inside the framework, making it harder to debug exactly why a trajectory went wrong or to enforce hard constraints on step order.
**Follow-ups.** Which of these would you pick for a production system that needs a deterministic audit trail for compliance? → LangGraph-style explicit graphs or a hand-rolled loop — both make the state transitions and checkpoints explicit and inspectable, whereas free-form multi-agent chat frameworks make it harder to guarantee reproducible, auditable step ordering.
**Page.** [[agent-frameworks-landscape]]

### Q8. Design a multi-agent system for a research-and-report task. What orchestration pattern would you use, and what coordination failure modes should you expect?
**Answer.** Use a supervisor pattern: one orchestrator agent decomposes the report into sections, dispatches a researcher-agent per section (each with web-search/retrieval tools), then a writer-agent synthesizes and a critic-agent reviews for contradictions before final output — rather than peer-to-peer free chat, which is harder to bound. Failure modes to expect: (1) *echo chambers* — sub-agents implicitly trusting and re-stating each other's unverified claims, amplifying an early hallucination; (2) *context loss at handoff* — the supervisor summarizing a sub-agent's output loses a caveat the next agent needed; (3) *redundant work* — two researcher agents covering overlapping sub-topics because task boundaries weren't disjoint; (4) *deadlock/loops* — critic keeps rejecting writer output on a criterion writer can't satisfy given the research gathered, with no escape hatch.
**Follow-ups.** How would you detect an echo-chamber failure in production rather than only in a demo? → Track claim provenance — require each sub-agent's factual claims to carry a source reference, and flag/audit any claim in the final report that can't be traced back to a retrieved source rather than another agent's prose.
**Page.** [[multi-agent-systems]]

### Q9. What is agentic RAG, and how is it fundamentally different from a fixed retrieve-then-generate pipeline?
**Answer.** Fixed RAG always retrieves once (or a hardcoded number of times) before generating, regardless of whether the query even needs retrieval or whether the first retrieval was sufficient. Agentic RAG makes retrieval a *tool* the model can choose to invoke, zero or many times, deciding dynamically whether to retrieve, reformulate the query and retrieve again, retrieve from a different source, or answer directly from parametric knowledge — the retrieval decision itself becomes part of the reasoning loop rather than a fixed pipeline stage.
**Follow-ups.** What's the cost/latency tradeoff of making retrieval agentic instead of fixed? → You trade a predictable one-shot retrieval latency for a variable number of round trips (each an LLM call plus a retrieval call), so tail latency and cost become much harder to bound — you typically need a hard cap on retrieval iterations to keep it production-viable.
**Page.** [[agentic-rag]]

### Q10. What does a computer-use / browser agent need beyond a text-and-tool-calling agent?
**Answer.** It needs a grounding mechanism to map a visual/DOM state to actionable coordinates or element references — either screenshot-based (the model reasons over pixel coordinates, which is fragile to resolution/layout shifts) or accessibility-tree/DOM-based (structured element references, more robust but not always available on arbitrary pages). It also needs a much richer, more error-prone action space (click, type, scroll, drag) where a single wrong coordinate silently does the wrong thing with no error thrown, unlike a malformed API call which fails loudly — so verification (a screenshot/state-diff after each action) becomes mandatory rather than optional.
**Follow-ups.** Why is a wrong click more dangerous than a wrong API call in this setting? → An API call with bad arguments typically errors and surfaces immediately; a wrong click on the wrong UI element can silently succeed (e.g. clicking "delete" instead of "archive") with no error signal at all, so the agent's internal state ("I clicked archive") diverges from ground truth with nothing forcing a correction.
**Page.** [[computer-use-and-browser-agents]]

### Q11. Where and how do you insert human-in-the-loop checkpoints in a production agent pipeline?
**Answer.** Insert them at points where the cost of a wrong autonomous action is asymmetric and hard to reverse — sending an external email, executing a financial transaction, deleting data, merging code — using an explicit interrupt/approval step that pauses the agent's state (not a side-channel notification the agent ignores) until a human approves, edits, or rejects the proposed action. Cheap, reversible, high-frequency actions (a read-only query, drafting text for review) shouldn't be gated, or the human becomes the bottleneck and the "autonomy" is fake.
**Follow-ups.** How do you avoid approval fatigue where a human just rubber-stamps every request? → Gate only genuinely high-stakes/irreversible actions, batch low-risk approvals, and track approve/reject rates per action type — if a checkpoint gets 99.9% blind approval, either the action isn't actually risky enough to need it or your UI isn't surfacing enough context for a real decision.
**Page.** [[human-in-the-loop-patterns]]

### Q12. What guardrails prevent an agent from running an unbounded loop or taking an unsafe action?
**Answer.** Structural guardrails: a hard max-step/max-token/max-cost budget per task that forces termination regardless of the model's own judgment; an allowlist of permitted tools and, within a tool, permitted argument ranges (e.g. a SQL tool restricted to read-only queries against specific tables); a repetition detector that halts if the same action-observation pair repeats (a stuck loop). Behavioral guardrails: validating tool outputs before feeding them back (don't let a scraped webpage's content silently become instructions — treat all tool output as untrusted data, not commands), and a separate, non-bypassable check for genuinely dangerous actions (destructive writes, spend above a threshold) that can't be talked around by clever prompting.
**Follow-ups.** Why is "ask the model to be careful" in the system prompt not a sufficient guardrail on its own? → Prompted instructions are soft constraints the model can be argued out of via adversarial input (prompt injection from tool output) or simply drift from under long contexts — real guardrails must be enforced in the harness code outside the model's control, not just requested of the model.

## Hard

### Q13. A multi-call agent's per-task cost is unpredictable. How do you actually bound and optimize latency/cost in production?
**Answer.** First make cost observable per-step (tokens in/out, tool latency) so you know where budget actually goes, not just the aggregate. Then apply layered controls: a hard step/cost ceiling per task with graceful degradation (return best-effort partial result rather than erroring past budget); route cheaper/smaller models for low-complexity sub-steps (a classifier-style routing decision or planning step) and reserve the frontier model for the steps that need it; cache tool results and even full sub-trajectories for repeated queries; parallelize independent sub-tasks instead of serializing them, since wall-clock latency in a sequential loop compounds every round trip. The core tension is that tighter budgets reduce cost/tail-latency but also cut off legitimate multi-step reasoning — so budgets should be tuned against measured task-completion-rate-per-dollar, not set arbitrarily.
**Follow-ups.** Why does naively parallelizing sub-tasks sometimes break correctness? → If sub-tasks share mutable state or later steps depend on earlier ones' outputs, running them concurrently can violate that dependency — you need an explicit dependency graph (which sub-tasks are truly independent) before parallelizing, not just fan-out everything.
**Page.** [[agent-cost-and-latency-optimization]]

### Q14. How do you evaluate an agent end-to-end, given that per-step accuracy doesn't tell you whether the overall task succeeded?
**Answer.** Per-step metrics (was this individual tool call correct) are necessary but not sufficient because an agent can make locally-correct choices that compound into a globally wrong outcome, or recover from a locally-wrong step and still succeed. Real agent evaluation needs task-level success metrics against a held-out set of realistic tasks with verifiable ground truth (did the report contain the right numbers, did the code pass the test suite, did the booking actually get made) — often via an LLM-judge rubric when there's no automatic checker, cross-validated against human judgment. You also need trajectory-level diagnostics (number of steps, number of retries, tool-call error rate) as leading indicators, since task-success rate alone doesn't tell you *why* failures happen.
**Follow-ups.** Why is LLM-as-judge evaluation of agent trajectories risky, and what do you do about it? → The judge model can share the same blind spots as the agent model (miss the same subtle factual errors) and is sensitive to surface features (verbosity, confident tone) rather than actual correctness — mitigated by grounding the judge in explicit, checkable rubric criteria and spot-checking judge verdicts against human review on a sample.
**Page.** [[agent-evaluation]]

### Q15. Trace a concrete multi-agent handoff failure: a researcher-agent's tool returns a stale or wrong number, and the writer-agent confidently includes it in the final report. Where do you intervene?
**Answer.** The failure has three intervention points, and fixing only the last one is insufficient. At the source: the researcher-agent should attach provenance (source URL/timestamp) to every extracted fact, not just the number, so staleness is at least checkable. At the handoff: the supervisor/critic step should require claims to be traceable to a cited source before passing them downstream, rejecting ungrounded numeric claims rather than passing prose summaries that strip the citation. At the sink: the writer-agent's system prompt/tooling should refuse to state a number without an accompanying citation, and a final verification pass (a citation-checker agent or heuristic) should confirm every numeric claim in the output actually appears in a retrieved source. Relying only on "tell the writer to double check" fails because by that point the provenance is already lost.
**Follow-ups.** How would this failure look different from a single-agent RAG hallucination, and does that change the fix? → In single-agent RAG the hallucination originates in generation over (possibly correct) retrieved context; here the *retrieval itself* returned bad data and it propagated structurally through agent handoffs — so the fix is about provenance-passing between agents, not just grounding the final generation step.
**Page.** [[multi-agent-systems]]

### Q16. When do you split a single ReAct agent with more tools into multiple specialized agents, versus just giving one agent a bigger toolbox?
**Answer.** Keep a single agent when the tools share context and the task genuinely needs one continuous reasoning thread over all of them — splitting adds coordination overhead (summarizing state across agent boundaries loses information) for no benefit. Split into specialized agents when: tool sets are large enough that a single system prompt with all tool schemas bloats context and confuses tool selection (empirically, model tool-selection accuracy degrades past a few dozen simultaneously available tools); sub-tasks require genuinely different "personas"/expertise framing that would otherwise conflict in one prompt (a strict compliance-checker persona vs a creative-drafting persona); or you need process isolation for safety (a code-execution agent's blast radius shouldn't be able to also send emails). The generic anti-pattern is splitting for its own sake — every extra agent boundary is a place information can silently get lost.
**Follow-ups.** What's a concrete signal in production logs that tells you a single agent has too many tools? → Tool-call error rate rising with tool-catalog size, or the model repeatedly choosing a plausible-but-wrong tool from a set of similarly-named/overlapping tools — a sign the model can't reliably disambiguate given the current toolbox.

### Q17. An agent's memory grows unbounded across a long-running conversation. How do you compact it without silently losing state the agent still needs?
**Answer.** Don't summarize blindly by token count — classify what's in the transcript first: durable facts (decisions made, user-stated constraints, entities/IDs referenced) versus disposable scratch reasoning (intermediate thoughts that were superseded). Persist the durable facts into a structured long-term store (key-value or a small retrievable index) rather than prose, so later retrieval is precise rather than "hope the summary mentioned it." For the rolling short-term window, use a sliding-window-plus-summary approach: keep the most recent N turns verbatim (recency matters for coherence) and replace older turns with a periodically regenerated summary, regenerating (not just appending to) the summary each time so it doesn't itself grow unbounded.
**Follow-ups.** What's the risk of summarizing with the same model that's running the agent loop, versus a dedicated summarization pass? → Doing it inline risks the summarization competing for the same context/attention budget as the task at hand and inheriting the same failure modes (it can hallucinate or drop a fact under the same pressures); a dedicated, narrowly-prompted summarization call with an explicit "don't drop these fields" checklist is more reliable and auditable.
**Page.** [[agent-memory]]

### Q18. Walk through what happens when the model emits malformed tool-call arguments (invalid JSON, wrong types, missing required fields) — how do frameworks actually handle this?
**Answer.** The harness validates the emitted arguments against the tool's declared schema before execution — never executes on faith. On a validation failure, well-built frameworks don't silently coerce or drop fields; they construct a structured error message (which field failed, why) and feed it back into the model's context as the "observation" for that turn, giving the model a chance to self-correct on the next generation, typically bounded to 1-2 repair attempts before the step is marked failed and escalated (to a fallback path or a human). The subtlety is that some models are more prone to this under certain conditions — deeply nested schemas, ambiguous enum values, or very long tool catalogs — so schema design (flat, unambiguous, well-described fields) is itself a lever for reducing malformed calls, not just downstream error handling.
**Follow-ups.** Why is silently coercing a malformed argument (e.g. casting a string "5" to int 5) worse than rejecting it? → Silent coercion can mask a genuine misunderstanding by the model (it meant a different field entirely) that would have surfaced as a visible error — you lose the debugging signal and risk the tool executing with subtly wrong semantics rather than failing loudly.
