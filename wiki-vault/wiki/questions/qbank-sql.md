# SQL Question Bank

> How to use: cover the answers, write yours first, then compare. Anything you fumble → the linked concept page's `status` should go back to `drafted`. This bank is deliberately conceptual/verbal — for hands-on query-writing practice, work through [[drill-sql-problems]] instead.

## Warm-up

### Q1. State SQL's logical execution order (not the order you type clauses) and explain one bug this order causes for beginners.
**Answer.** Logical order: `FROM`/`JOIN` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `DISTINCT` → `ORDER BY` → `LIMIT`. It's not the typed order because `SELECT` is written first but evaluated almost last. The classic bug: you can't reference a `SELECT`-defined column alias inside `WHERE` (`WHERE revenue_per_user > 10` when `revenue_per_user` is an alias defined in `SELECT`) because `WHERE` executes before `SELECT` even exists yet — the alias doesn't exist at that point in logical evaluation, even though most engines let you reference it in `ORDER BY`, which runs after `SELECT`.
**Follow-ups.** Why does `HAVING` exist as a separate clause instead of just letting `WHERE` filter on aggregates? → `WHERE` filters rows before grouping happens, so it has no aggregate value to test yet; `HAVING` runs after `GROUP BY` produces one row per group, at which point aggregate values like `SUM(x)` actually exist to filter on.
**Page.** [[sql-fundamentals]]

### Q2. Why does `WHERE` silently drop rows that `HAVING` would have kept, when both look like they're filtering "the same thing"?
**Answer.** They filter at different grains: `WHERE` filters individual rows *before* aggregation, so a row excluded there never contributes to any group's aggregate at all — the group's `SUM`/`COUNT` is computed as if that row never existed. `HAVING` filters whole groups *after* aggregation, using the aggregate's final value — every row still contributed to the aggregate before the group itself got filtered out. Swapping a condition from one to the other by mistake (e.g. putting `WHERE amount > 0` when you meant `HAVING SUM(amount) > 0`) changes which rows influence the aggregate, not just which final rows appear.
**Follow-ups.** Can you use a column in `WHERE` that isn't in the `SELECT` list or `GROUP BY`? → Yes — `WHERE` only needs the column to exist in the underlying table(s) being scanned, since it runs before grouping/projection reduce what's available.
**Page.** [[aggregations-and-grouping]]

### Q3. A `LEFT JOIN` between a 1000-row `orders` table and a `customers` table returns 1200 rows. What does that tell you, and what would an `INNER JOIN` on the same tables have returned?
**Answer.** A `LEFT JOIN` preserves every row from the left table at least once, and produces one output row *per matching right-side row* — so 1200 > 1000 means at least one `order` matched *multiple* `customers` rows (a fan-out, usually meaning `customers` isn't unique on the join key — a data quality problem, not a SQL bug). An `INNER JOIN` on the same tables would return only the rows where a match exists at all — fewer than or equal to 1200, and it would silently drop any order whose customer_id doesn't exist in `customers`, which a `LEFT JOIN` would have kept (with nulls on the customer side).
**Follow-ups.** How do you defend against this exact fan-out bug before it ships? → Assert row-count invariants before/after a join in a test or pipeline check (`assert result.count() == orders.count()` when you expect a 1:1 join), and verify the "many" side of any join is actually unique on the join key ahead of time.
**Page.** [[joins-deep-dive]]

### Q4. When do you reach for a CTE over a subquery, and when does either turn into a performance problem?
**Answer.** A CTE (`WITH x AS (...)`) is chosen for readability — naming an intermediate result so a multi-step query reads top-to-bottom instead of nesting parentheses several levels deep — and for reusing the same intermediate result multiple times in one query without repeating the SQL. A correlated subquery, by contrast, re-executes once per outer row, which becomes a performance problem at scale precisely because that "once per row" cost isn't obvious from reading the SQL. Most modern engines (Postgres 12+, Spark SQL) inline a non-recursive CTE into the query plan exactly like an equivalent subquery — so the choice is about readability, not performance, unless the engine specifically materializes CTEs (some engines historically forced materialization, turning a CTE into an optimization barrier the planner couldn't see through).
**Follow-ups.** What's the one thing a CTE can do that a plain subquery can't? → Recursive CTEs (`WITH RECURSIVE`) — self-referencing to walk a hierarchy (an org chart, a bill-of-materials tree) — a plain subquery has no way to reference itself.
**Page.** [[subqueries-and-ctes]]

### Q5. Explain the difference between `ROW_NUMBER()`, `RANK()`, and `DENSE_RANK()` with a concrete tie.
**Answer.** Given ordered values `[100, 90, 90, 80]`: `ROW_NUMBER()` gives `1,2,3,4` — always a strict, arbitrary tiebreak among equal values, never repeating a number. `RANK()` gives `1,2,2,4` — ties share a rank, but the *next* rank skips ahead by the number of tied rows (gap after a tie). `DENSE_RANK()` gives `1,2,2,3` — ties share a rank with no gap afterward. The choice matters concretely for "top-N per group": using `ROW_NUMBER()` when ties exist silently and arbitrarily picks one row to be "the" top row, which is wrong if you actually want every tied row returned.
**Follow-ups.** Which of the three would you use to assign dense, gapless tier numbers to customers by spend for a loyalty program? → `DENSE_RANK()` — you want ties grouped into the same tier with no skipped tier numbers afterward.

## Core

### Q6. Explain the difference between a window function's `ROWS BETWEEN` and `RANGE BETWEEN` frame clause, with a case where they give different answers.
**Answer.** `ROWS BETWEEN` counts physical rows regardless of value ties — `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` always spans exactly 3 physical rows. `RANGE BETWEEN` counts *logical* peer groups by value — `RANGE BETWEEN 2 PRECEDING AND CURRENT ROW` on an `ORDER BY amount` includes every row whose `amount` falls within that value range, which can be more or fewer than 3 rows if ties exist on the ordering column. They diverge concretely on a running total over a column with duplicate values: `SUM(x) OVER (ORDER BY date RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)` with two rows sharing the same `date` includes *both* tied rows' values in each of their own running totals (same logical peer group), while `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` gives each tied row a different running total based on its arbitrary physical position.
**Follow-ups.** Which one is the default frame when you write `ORDER BY` in a window function without specifying a frame clause at all? → `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` is the SQL-standard default — a common source of surprise when ties on the order column exist and you expected `ROWS` semantics.

### Q7. What's the conceptual difference between `GROUP BY ROLLUP` and `GROUP BY GROUPING SETS`, and when would you actually reach for either instead of writing a `UNION ALL` of separate aggregate queries?
**Answer.** `ROLLUP(a, b, c)` produces a fixed hierarchical set of subtotals — `(a,b,c)`, `(a,b)`, `(a)`, `()` — mirroring a drill-down hierarchy (region → store → product, say), computed in one pass over the data. `GROUPING SETS` lets you specify an arbitrary, non-hierarchical list of grouping combinations you actually want (e.g. `(region, product)` and `(store)` with no shared hierarchy) in one query. Both exist to avoid scanning the base table once per subtotal level via `UNION ALL` of separate `GROUP BY` queries — the engine computes all requested grouping levels in a single pass, which matters a lot once the base table is large enough that repeated full scans are the dominant cost.
**Follow-ups.** How do you tell which rows in the result are a subtotal versus a real leaf-level group when both can have the same-looking `NULL` in a grouping column? → The `GROUPING(col)` function returns `1` for a row where `col` is `NULL` *because it was rolled up*, and `0` when `col` is a genuine `NULL` value in the data — disambiguating a real null from an aggregation placeholder.
**Page.** [[aggregations-and-grouping]]

### Q8. Without writing code, explain the general technique behind "gaps and islands" problems (consecutive login streaks, session grouping, contiguous date ranges) and why it reduces to a plain `GROUP BY`.
**Answer.** The trick is finding some derived value that stays *constant* across every row within one "island" (a contiguous run) and *changes* at every boundary between islands — once you have that, grouping by it is a normal aggregate query. Two common ways to derive it: (1) for a strictly-consecutive sequence like dates, subtract a `ROW_NUMBER()` (which increments by exactly 1 per row) from the sequence value itself — inside a consecutive run both increment in lockstep, so the difference is constant, and it jumps at every gap; (2) for an arbitrary gap threshold (e.g. "new session after 30 minutes idle"), compute a running `SUM()` of a 0/1 "is this a new island?" flag (itself derived from `LAG()` comparing consecutive rows) — the running sum is flat within an island and increments exactly at each boundary. Either way, "find contiguous runs" becomes "compute one constant-within-run column, then `GROUP BY` it."
**Follow-ups.** Why does this pattern specifically need a window function and not just `GROUP BY` on the raw data? → Because "is this row part of a new island" is inherently a comparison to the *previous row in order*, which plain `GROUP BY` has no concept of — window functions are the only standard-SQL mechanism for row-to-row ordered comparisons without a self-join.

### Q9. Explain, conceptually, the difference between a B-tree index and a hash index, and name a query pattern where an index on a column provably won't help at all.
**Answer.** A B-tree index keeps keys in sorted order in a balanced tree, supporting equality *and* range queries (`>`, `<`, `BETWEEN`, and range/prefix matches like `LIKE 'abc%'`) in $O(\log n)$. A hash index maps a key to a bucket via a hash function — equality lookups are $O(1)$-ish, but it has no concept of order, so it can't serve a range query at all. An index provably doesn't help when the leading condition isn't sargable: a leading wildcard (`LIKE '%abc'`) can't use a B-tree's sort order (you'd need to scan from every possible starting point), and wrapping the indexed column in a function (`WHERE UPPER(email) = 'X'`) prevents the planner from using a plain index on `email` unless a matching functional/expression index exists.
**Follow-ups.** Why does an index sometimes make a query *slower* to plan for, even though the column is indexed? → If the column has low selectivity (few distinct values relative to row count, e.g. a boolean `is_active` flag), the optimizer correctly estimates that a full table scan reading sequentially will beat the random I/O pattern of index lookups plus a row-by-row heap fetch for a large fraction of the table — so the planner ignores the index by design, not by mistake.

### Q10. Walk through how you'd read an `EXPLAIN` plan to diagnose a slow query, and name the three join algorithms a planner chooses between.
**Answer.** Read bottom-up and outside-in: the innermost/lowest nodes are base table access (`Seq Scan` vs `Index Scan` vs `Index Only Scan` — the last needs no heap fetch because every needed column is in the index itself), and the tree above shows how those scans combine. Look at estimated vs. actual row counts at each node (a huge mismatch signals stale statistics, which misleads every join-order decision above it) and where the time is actually spent (`EXPLAIN ANALYZE` gives real timings, not just estimates). The three join algorithms: nested loop (fine for a small outer side or when the inner side is index-accessible per row — bad at scale otherwise since it's effectively $O(n \times m)$), hash join (build a hash table on the smaller side, probe with the larger — good general-purpose choice for large unsorted inputs on equality joins), and merge join (both sides already sorted on the join key — merge in one linear pass, excellent when the sort is free because an index already provides it).
**Follow-ups.** What's the single most common root cause behind a planner picking a badly wrong join algorithm or join order? → Stale or missing table statistics (row counts, value distribution histograms) — the cost-based optimizer is only as good as its cardinality estimates, and a large estimate-vs-actual gap cascades into wrong decisions at every node above it.

### Q11. A junior analyst wants to fully normalize (3NF) the fact table in a reporting warehouse "to avoid data duplication." Why is that usually the wrong call, and when would 3NF actually be the right design?
**Answer.** A 3NF-normalized schema is optimized to make single-row transactional writes safe and non-redundant (an OLTP goal) — every update touches exactly one place, at the cost of needing many joins to reconstruct a full picture for reading. A reporting/OLAP warehouse's dominant workload is the opposite: read-heavy, scan-heavy aggregate queries over a mostly-static historical fact table, where extra joins are pure cost with no write-safety benefit gained (nobody's doing single-row transactional updates against the fact table). A star schema deliberately denormalizes dimension attributes (e.g. product category name lives directly on `dim_product`) to minimize joins on the hot read path, accepting some redundancy because dimension tables are small and slow-changing enough that the redundancy costs little and update anomalies are a non-issue. 3NF is still the right call in the OLTP system feeding the warehouse in the first place — the source-of-truth transactional database — just not in the analytics layer built to be read.
**Follow-ups.** What's the actual cost you're accepting by denormalizing, and how is it usually managed? → Update anomalies — if a product's category name changes, every fact row's denormalized copy is now stale until the dimension table (and its downstream materializations) is refreshed; managed by controlling denormalization to slowly-changing, low-cardinality dimension attributes and rebuilding/upserting dimensions on a defined schedule rather than denormalizing high-churn data.

### Q12. Explain the difference between a semi-join (`WHERE EXISTS`) and an anti-join (`WHERE NOT EXISTS`), and the classic `NOT IN` bug that makes anti-joins dangerous with nullable columns.
**Answer.** A semi-join returns rows from the left table that have *at least one* match in the right table, without duplicating the left row per match (unlike a real `JOIN`, it never fans out) — `WHERE EXISTS (SELECT 1 FROM b WHERE b.key = a.key)` is the idiomatic form. An anti-join is its negation — left rows with *no* match at all — `WHERE NOT EXISTS (...)`. The classic bug: `WHERE a.key NOT IN (SELECT key FROM b)` silently returns **zero rows**, for every input, the moment the subquery's result set contains even one `NULL` — because `x NOT IN (1, NULL)` evaluates to `NOT (x=1 OR x=NULL)`, and `x=NULL` is `UNKNOWN` rather than `FALSE`, poisoning the whole `OR`/`NOT` into `UNKNOWN` (excluded) for every row. `NOT EXISTS` has no such trap because it only ever tests for the *existence* of a matching row, never evaluating an equality against a literal `NULL` value in a list.
**Follow-ups.** Given that trap, why would anyone still use `NOT IN` at all? → It reads more naturally for a genuinely non-null, small, hardcoded literal list (`WHERE status NOT IN ('cancelled', 'refunded')`) — the danger is specifically a *subquery-derived* list, which can silently contain an unexpected `NULL` you didn't audit for.

## Hard

### Q13. Design the SQL-level mechanics for consuming a change-data-capture (CDC) feed into a warehouse table — what does the upsert logic actually need to handle, beyond "insert new rows"?
**Answer.** A CDC feed delivers a stream of row-level events tagged insert/update/delete against a source table; consuming it correctly means the target table's state after applying a batch of events must match the source's state as of that point, not just accumulate history. The core operation is `MERGE INTO target USING cdc_batch ON target.key = cdc_batch.key WHEN MATCHED AND cdc_batch.op = 'delete' THEN DELETE WHEN MATCHED THEN UPDATE SET ... WHEN NOT MATCHED AND cdc_batch.op != 'delete' THEN INSERT ...` — one atomic statement handling all three operations against the current state. Two subtleties that break naive implementations: out-of-order delivery (a batch can contain an update and a later delete for the same key — you must keep only the *latest* event per key per batch, typically via a `ROW_NUMBER() OVER (PARTITION BY key ORDER BY change_sequence DESC) = 1` filter before the merge) and re-delivery/at-least-once semantics (the same event arriving twice must be a no-op, which `MERGE`'s idempotent match-then-apply behavior naturally gives you as long as you're merging on the same key and applying the same final state, not blindly re-inserting).
**Follow-ups.** In a Databricks/Delta Lake setting specifically, what feature exists to avoid hand-rolling the CDC consumption logic yourself? → Delta Lake's Change Data Feed (`CDF`) exposes a table's own row-level changes as a queryable stream (`table_changes()`), and `MERGE INTO` combined with `CDF` is the standard building block for propagating changes silver→gold without re-deriving "what changed" from scratch each run.

### Q14. Write a recursive CTE conceptually (describe the anchor and recursive parts) for finding every employee under a given manager in an arbitrarily deep org chart, and explain why a fixed number of self-joins can't solve this in general.
**Answer.** A recursive CTE has two parts unioned together: an anchor member (`SELECT id, manager_id, 0 AS depth FROM employees WHERE id = :root_id`) that seeds the starting row, and a recursive member (`SELECT e.id, e.manager_id, r.depth + 1 FROM employees e JOIN recursive_cte r ON e.manager_id = r.id`) that repeatedly joins the growing result set back against the base table, re-executed until it produces no new rows. A fixed chain of `N` self-joins can only ever resolve exactly `N` levels of hierarchy — it has no way to keep going for an org chart that happens to be 8 levels deep in one branch and 3 in another, because the join depth is baked into the query text at write time, not determined by the data at run time; a recursive CTE's termination is data-driven (stops when a level produces zero new rows), so it handles arbitrary and uneven depth correctly.
**Follow-ups.** What's the standard safeguard against an accidental infinite loop if the underlying data has a cycle (e.g. a manager_id loop due to a data bug)? → Most engines support a `MAXRECURSION`/statement-level recursion limit that aborts past a threshold, and defensively you can also carry a visited-set or depth cap inside the recursive member itself to bail out deliberately rather than relying on the engine's default limit.

### Q15. A query that used to run in 2 seconds suddenly takes 40 seconds after a large nightly data load, with no code change. Walk through the diagnosis.
**Answer.** The first suspect, before touching the query itself, is stale planner statistics: after a large bulk load, the table's row count and value-distribution histograms the optimizer relies on for cardinality estimation are now badly out of date relative to reality, and a cost-based optimizer making decisions off wrong estimates can flip a join order or join algorithm choice entirely (e.g. switching from a cheap index-nested-loop to an expensive full hash join, or vice versa, because it now believes a table is a different size than it is). The fix is usually running the engine's statistics-refresh command (`ANALYZE` in Postgres, `ANALYZE TABLE ... COMPUTE STATISTICS` in Spark/Hive) and re-running `EXPLAIN ANALYZE` to confirm the plan changed back to something sane — only after ruling that out would you look at genuine data growth outpacing an index's effectiveness, or a newly-introduced data skew in a join key.
**Follow-ups.** Why do some pipelines explicitly schedule a statistics refresh as a required step immediately after every bulk load, rather than relying on automatic/background stats collection? → Automatic stats collection is often triggered by a mutation-count threshold or runs on a schedule that may lag well behind a single large batch load — for a pipeline where query performance right after load matters, an explicit synchronous `ANALYZE` step removes the race between "data changed" and "planner found out."

### Q16. You're computing a 7-day trailing distinct-user count as a window function over a large `events` table in Spark SQL, and it's dramatically slower than a simple `SUM() OVER` moving average on the same window. Why, specifically, and what would you do instead at scale?
**Answer.** `SUM() OVER (ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)` is a genuinely incremental computation — each new row's window value can be derived from the previous window's value plus/minus one row entering/leaving, so the engine never needs to re-scan the whole window per output row. `COUNT(DISTINCT user_id) OVER (...)` cannot be computed incrementally the same way, because removing a row that leaves the trailing window might have been the *only* occurrence of that user in the window — you can't just subtract 1, since you don't locally know whether another occurrence of that same user is still inside the window without re-examining it; most engines fall back to materializing the full distinct set per window frame, which is effectively quadratic in the window size across the whole dataset. At scale, the standard workarounds are: pre-aggregate to a per-user, per-day "was active" flag and reformulate as counting flag rows differently, or accept approximate distinct counts via `HyperLogLog` sketches (mergeable, so a 7-day sketch is a cheap union of 7 daily sketches) instead of exact `COUNT(DISTINCT)`.
**Follow-ups.** Why does the HyperLogLog-sketch approach specifically solve the incremental-computation problem that broke the naive `COUNT(DISTINCT)`? → HLL sketches are mergeable (algebraically composable) — a 7-day sketch is just the union of 7 one-day sketches, so sliding the window by one day is one cheap merge operation of small sketches rather than a full re-scan of raw rows, trading exactness for that incremental structure back.
